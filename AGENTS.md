
## music-diary
 
Платформа-блог для музыкальных дневников. Каждый зарегистрированный пользователь
ведёт свой блог: посты — это личный текст + прикреплённый трек, подтянутый через
внешний API. Вся творческая часть (текст, рефлексия) хранится в своей базе;
внешний API отвечает только за метаданные трека (название, артист, обложка,
превью).
 
## Стек
 
- Next.js 16+ (App Router), React 19, TypeScript
- Prisma + PostgreSQL (Supabase)
- Better Auth
- Tailwind CSS
- Supabase Storage — только для аватаров пользователей; обложки треков приходят по URL от внешнего API, свой storage для них не нужен
## Команды
 
```bash
npm run dev          # локальный дев-сервер
npm run build         # прод-сборка
npm run lint           # ESLint
npx prisma studio    # визуальный просмотр БД
npx prisma migrate dev --name <имя>   # новая миграция
```

**Друзья (взаимные, кнопка на `/u/[username]`, публичный список `/u/[username]/friends`, приватный хаб `/friends`)** — сосуществует с подписками, не замена: у `Follow` нет подтверждения, у дружбы есть заявка + принятие
| Файл | Что там |
|---|---|
| `prisma/schema.prisma` | `FriendRequest` (заявка, `senderId`/`receiverId`) и `Friendship` (уже состоявшаяся дружба) — две отдельные модели, не расширение `Follow`: связь взаимная, с промежуточным состоянием заявки, `Follow` под это не подходит. В `Friendship` всегда `userAId < userBId` (обычное сравнение строк) — один ряд на пару, а не «кто кого»; инвариант держится только в коде (`normalizePair`), в БД никак не проверяется. `FriendRequest.ignoredAt DateTime?` — «Позже» (см. подсекцию про тост): дата, а не boolean, чтобы позже можно было сделать авто-возврат через N дней |
| `lib/friends.ts` | `normalizePair(a, b)` — единственное место, которое решает порядок пары; `getFriendshipStatus(myId, targetId)` → `"none" \| "friends" \| "pending_outgoing" \| "pending_incoming"` для кнопки; `getFriends`, `getIncomingFriendRequests` (только `ignoredAt: null`), `getDeferredFriendRequests` (только отложенные), `getOutgoingFriendRequests`. `getFriendshipStatus` про `ignoredAt` **не знает намеренно** — на профиле отправителя отложенная заявка выглядит как обычная входящая, «Позже» глушит счётчики, а не саму заявку |
| `lib/friend-actions.ts` | мутации — в `lib/`, а не в `actions.ts` одного роута, т.к. дергаются минимум с трёх мест (кнопка на дневнике, входящие/исходящие в хабе), та же причина, что у `lib/like-actions.ts`. `sendFriendRequest` — если у адресата уже есть встречная заявка к отправителю, это не второй `FriendRequest`, а сразу `$transaction`(удалить встречную заявку + создать `Friendship`) — без этого заявки от A и B друг к другу зависли бы обе, и никто явно не жал "Принять". Везде `revalidatePath` для обеих сторон (`/u/[username]` × 2, `/u/[username]/friends` × 2, `/friends`) — шире, чем у `toggleFollow`, которая ревалидирует только целевого пользователя. `ignoreFriendRequest` — `updateMany`, а не `update`: повторный клик по уже отложенной (или отменённой отправителем) заявке штатен, `update` кинул бы исключение на ноль строк. **Заявка живёт в двух направлениях сразу** (A и B нажали «Добавить» одновременно → оба прочитали пустую встречную и оба создали свою), поэтому всё, что закрывает вопрос дружбы, чистит обе стороны через хелпер `pairRequests` — и `acceptFriendRequest`, и ветка автопринятия в `sendFriendRequest`. Иначе пережившая строка становится вечной входящей от уже состоявшегося друга: «Принять» по ней падает об unique на `Friendship`, а счётчик в шапке залипает намертво (выход только «Отклонить», до чего надо догадаться). Плата за `deleteMany` — от двойного принятия защищает только unique на `Friendship`, и это осознанный размен. У `sendFriendRequest` есть гард «уже друзья» (`friendship.findUnique` до всего остального) — экшен это публичный POST-эндпоинт, и прямой вызов при существующей дружбе создавал бы ту же фантомную заявку; возвращает `status: "friends"`, а не `error`, иначе `useOptimistic` в `FriendButton` откатил бы кнопку в «Добавить в друзья». `cancelFriendRequest`/`declineFriendRequest` — тоже `deleteMany`, но **по одному направлению**: отмена своей исходящей не должна заодно стирать входящую от того же человека, это разные действия |
| `components/FriendButton.tsx` | client, по образцу `FollowButton`, но состояние не boolean, а 4 варианта; `pending_incoming` рендерит сразу две кнопки (Принять/Отклонить) вместо одной. После каждого действия зовёт `refresh()` из `useNotifications()` — иначе цифра в шапке не сдвинется |
| `components/IncomingRequestRow.tsx`, `components/OutgoingRequestRow.tsx` | строки для `/friends`: аватар+имя кликабельны отдельной `<Link>`, кнопки действия — рядом, не внутри неё (`<button>` внутри `<a>` — невалидная вложенность). `UserResultRow` тут не подошёл: он сам целиком `<Link>`, кнопку действия внутрь не вставить. ## Дизайн-система «тёплый зин» (первый заход 2026-08-20)

До этого сайт стоял на боилерплейте Next: два токена (`--background`/`--foreground`),
цвета руками в разметке, `Arial` в `body`. Направление выбрано разработчиком из трёх
предложенных (тёплый зин / тёмная студия / строгий минимал): кремовая бумага, тёплый
чёрный вместо чистого, один акцент-терракота, текст записей — антиквой.

**Что важно помнить:**

- **`dark:`-вариантов в новой разметке быть не должно.** Цвета живут переменными в
  `:root` и переопределяются в `@media (prefers-color-scheme: dark)`, а `@theme inline`
  раздаёт из них утилиты (`bg-surface`, `text-muted`, `border-line`). Компонент пишет
  один класс, тёмная тема получается сама. Раньше `border-black/[.08] dark:border-white/[.145]`
  был захардкожен в 30 файлах.
- **Переключателя темы нет** — тема жёстко следует системной. Токены к нему готовы
  (нужен только `[data-theme]`-селектор рядом с медиа-запросом), но сам переключатель
  не делался.
- **Шрифт был сломан двумя независимыми способами**: `body { font-family: Arial }` из
  боилерплейта перебивал Geist, и вдобавок `subsets: ["latin"]` не грузил кириллические
  глифы — русский текст уезжал в системный фолбэк. Обе причины чинились по отдельности;
  при добавлении любого нового шрифта проверять `subsets`.
- **`.prose-diary` — единственный «типографский» класс**, для текста записей (Literata,
  увеличенный интерлиньяж). Интерфейс остаётся на Geist: антиква только там, где читают.
- **`lib/artwork.ts`** — обложки лежат в базе в 100×100 (`artworkUrl100` от iTunes), для
  крупного героя это мыло. Размер зашит в сам URL, поэтому апскейл — подмена сегмента
  на лету, без миграции данных и повторного похода в API. Адреса Cover Art Archive
  (MusicBrainz) под регулярку не попадают и возвращаются как есть — штатная ветка.
- **`PostCard` строит карточку вокруг первого трека**: его обложка — герой слева,
  остальные треки идут списком `TrackRow` ниже. У поста без текста (штатный случай —
  «только трек») содержимое центрируется по обложке, иначе под ней зияет дыра.
- **Заход был пилотным: перекрашены только шапка, лента `/` и общие атомы**
  (`PostCard`, `TrackRow`, `Avatar`, `LikeButton`, `SessionStatus`, `SignOutButton`).
  Дальше добавились экраны состояний (2026-08-27), страница записи
  `/u/[username]/[slug]` и дневник автора `/u/[username]` вместе со списком
  друзей (2026-08-28), пишущий путь `/new` и `/post/[id]/edit` (2026-08-29),
  личные экраны `/friends`, `/messages`, `/messages/[username]` и `/following`
  (2026-08-31) — у всех свои секции ниже. Остальные страницы
  (`/settings`, `/search`, `/login`, `/signup`) **всё ещё на старых
  классах** `border-black/[.08]`, `bg-white`, `text-zinc-*` — на кремовом фоне они
  выглядят чужеродно. Это не забытый хвост, а осознанная граница: перекрашивание
  идёт заходами, каждый проверяется глазами целиком. Критерий готовности захода —
  грепом: `grep -rnE "dark:|bg-white|text-zinc-|border-black/\[\.08\]" <файлы>`
  должен молчать.

### Экраны состояний на знаке (2026-08-27)

До этого в проекте не было ни одного `loading.tsx`/`error.tsx`. Знак уже умел
два глагола — «рисуется при появлении» и «дышит, пока играет превью», — и из них
достроился словарь состояний, общий для веба и будущего приложения: **тишина
(`Groove silent`) · песня (`waveline--live`) · письмо (`waveline--writing`) ·
обрыв (`variant="broken"`)**.

| Файл | Что там |
|---|---|
| `app/loading.tsx` | корневой лоадер: знак **пишется** — `stroke-dashoffset` едет не до нуля, а дальше в минус, штрих набегает слева и уходит за правый край, по кругу. Дыхание занять было нельзя, оно уже означает «играет превью», и лоадер соврал бы. Текста нет намеренно — только `sr-only` внутри `role="status" aria-live="polite"`, иначе переход для незрячего выглядит тишиной. Обёртка на `.appear-delayed`: локально страницы отвечают за ~80 мс, и без задержки лоадер мигает вспышкой, читается как глитч |
| `app/error.tsx` | `"use client"` обязателен — Next вешает сюда error boundary, а он живёт только на клиенте. Знак в `variant="broken"`, кнопка зовёт `reset()` (перемонтирует сегмент без полной перезагрузки). Текст ошибки пользователю не показываем: в проде Next всё равно подменяет его обезличенным |
| `app/not-found.tsx` | корневой 404, тот же `broken`. Ловит всё, у чего нет своего `not-found` ниже по дереву (у дневника и у записи он свой) |
| `components/Waveline.tsx` | проп `writing?: boolean` и вариант `broken` в `SHAPES`. `broken` — не «всплеск наоборот», а своя геометрия: ровная нить, разрыв, концы отклонены **зеркально**. Параллельные концы читались как «//», то есть просто пунктуация; зеркало даёт излом. `broken` **не дышит** под играющее превью — «оборвалось» не должно приплясывать под трек |

**Грабля, стоившая отладки: `calc()` с `var()` внутри `@keyframes` не интерполируется.**
Первая версия писала `to { stroke-dashoffset: calc(var(--stroke-len) * -1) }` — и знак
скачками прыгал между двумя невидимыми краями вместо плавного хода. `getKeyframes()`
показал причину: браузер оставил значение как `calc(-110px)` (значения с `var()`
резолвятся поздно), интерполировать такое он не умеет и переключается на **дискретную**
анимацию. Лечится второй переменной (`--stroke-len-neg`), которую компонент отдаёт
готовым числом. Симптом обманчив: `getComputedStyle` показывает живой `animationName`
и `playState: "running"` — анимация действительно идёт, просто ступенькой.

Тайминг `linear`, а не `ease-in-out`: плавная кривая тормозит у краёв цикла, а края
здесь — это как раз мгновения, когда штрих спрятан целиком.

В `@media (prefers-reduced-motion: reduce)` у `.appear-delayed` `animation: none`
обязано идти **в паре с `opacity: 1`** — иначе выключенная анимация оставляет базовый
`opacity: 0` и экран загрузки становится пустым. У `.waveline--writing` такой пары не
нужно: база `stroke-dashoffset: 0` оставляет штрих нарисованным, статичный знак —
правильный исход.

**Где знак встречается — ровно три роли** (логотип в шапке · разделитель внизу
карточки, через одну · конец ленты) плюс иконка вкладки. На главной это 6
вхождений на семи записях.

**История решения важнее самого списка.** Первый заход раскидал знак по десяти
местам (~27 вхождений на главной): маркер трека вместо `▸` в каждой карточке,
между записями ленты, под заголовками сайдбара, под приветствием, в модалке
поиска, открывал и закрывал первый экран. Разработчик это свернул одной фразой —
«не должно быть чересчур попсовым». И был прав: знак, встречающийся 27 раз,
перестаёт быть подписью и становится узором на обоях; тату работает потому,
что оно одно. **Не размножать обратно** — оценивать идеи со знаком вычитанием,
а не сложением.

Чередование через карточку — свойство *списка*, поэтому решает `app/page.tsx`
(`showMark={index % 2 === 0}`), а не сама карточка. Сознательно проп, а не
глобальное CSS-правило `:nth-child(even)`: оно молча сработало бы на всех ещё
не перекрашенных страницах с карточками. Пропущенная карточка получает не
пустоту, а `Groove silent` — ровную нить: иначе у одних записей лайки отделены
линией, у других висят в воздухе, и это читается как баг вёрстки, а не замысел.

**Все знаки дышат разом**, когда где угодно на странице играет превью — каждый
это client-компонент, подписанный на контекст плеера. Проверено вживую ещё на
27 листьях, так что запас прочности есть; если когда-нибудь станет много —
вынести чистый SVG в серверный компонент, клиентскую обёртку оставить только
там, где нужна реакция.

**Линовка страницы** (`body::before` в `app/globals.css`): сайт лежит на тетрадном
листе — это дневник, линейка тут самая честная метафора. Повторяющийся градиент,
ассета нет; карточки непрозрачны (`bg-surface`) и накрывают её, поэтому линовка
видна только в полях и промежутках. Маска сверху не даёт первому экрану выглядеть
расчерченным бланком. Токен `--rule` — рядом с остальной палитрой, своя пара
значений в тёмной теме. `body::after` при этом занято зерном — не перепутать.

### Мобильная шапка: разделы под кнопкой меню (2026-08-31)

Не перекраска, а баг вёрстки, найденный скриншотами захода B и подтверждённый
в заходе C: у **залогиненного** в шапке семь элементов в строку, на 390 px они
растягивали документ до ~745 px, и страница ехала вбок на каждом экране сайта.
У анонима (`Войти` + `Регистрация` ≈ 340 px) всё влезало и влезает — чинился
только залогиненный вид. Чинилось первым, до оставшихся заходов перекраски:
иначе их мобильные скриншоты снимались бы на съезжающей странице.

Подход выбран разработчиком — **меню-панель**. Отклонены: «всё в иконки»
(иконками не различить «Мой дневник» и «Мою ленту» — обе «список записей»,
плюс ряд иконок в тёплом зине читается как панель приложения, а не тетрадь)
и «липкая полоса внизу» (новый паттерн, которого в проекте нет, и постоянно
отъедает низ экрана там, где читают записи).

| Файл | Что там |
|---|---|
| `components/MobileMenu.tsx` | кнопка-«три полоски» под `sm:hidden` + панель на нативном `<dialog>` — **третье применение идиомы** после `SearchDialog` и `TrackPickerDialog`, Esc/ловушка фокуса/`backdrop:bg-ink/40` достаются даром. Компонент **презентационный: своих хуков не зовёт**, принимает `username`/`requestCount`/`unreadMessages` пропсами — сессия читается по-прежнему в одном месте, а меню остаётся тупым и проверяемым. Панель прижата к правому верху под шапку (`ml-auto mr-3 mt-16`), а не выезжает во весь экран сбоку: разделов шесть, полноэкранная штора под них — это уже хром приложения. Клик по ссылке закрывает панель **обработчиком на контейнере** (`closest("a")`), а не колбэком на каждой ссылке: навигация клиентская, сам `<dialog>` о ней не узнает. Здесь же живёт `NavBadge` — плашка-счётчик переехала сюда из `SessionStatus` только чтобы не заводить кольцо импортов (`SessionStatus` и так тянет это меню) |
| `components/SessionStatus.tsx` | ряд разделов завёрнут в `hidden sm:flex`, рядом `<MobileMenu>`; хуки (`authClient.useSession`, `useNotifications`) остались здесь. «Добавить запись» на `< sm` сокращается до «Записать» двумя `<span>` — в меню её прятать нельзя, это главное действие сайта, а полный текст ест ~150 px |

**Точка на кнопке меню обязательна.** Счётчики заявок и непрочитанных уехали
внутрь панели, а весь их смысл — попадаться боковым зрением. Снаружи остаётся
одна акцентная точка при `requestCount + unreadMessages > 0`: она не говорит
«сколько», но говорит «загляни»; точные числа — прежним `NavBadge` внутри.
Точка того же `bg-accent`, что бейдж непрочитанного в `ConversationRow` —
язык уведомлений на сайте один.

**Кнопка меню не нарисована фирменным знаком** — у знака уже три роли, четвёртая
сделала бы из него узор (правило «не размножать обратно»). Обычные три полоски,
которые заодно рифмуются с линовкой страницы.

**Грабля Playwright, стоившая трёх ложных таймаутов логина:** скрипт жал «Войти»
**до гидратации**. React ещё не навесил `onSubmit`, а контролируемые поля
обнулялись после `fill()` — форма молча не отправлялась: ни ошибки на экране,
ни запроса к `/api/auth/sign-in/email`, симптом неотличим от «неверный пароль»
или «сервер не отвечает». Лечится `waitUntil: "networkidle"` плюс явная пауза
перед `fill()`. Логин при этом честно укладывается в пару секунд — прежний
совет про 90-секундный таймаут остаётся для прод-сборки, но здесь виноват был
не он.

**Проверено:** `document.documentElement.scrollWidth` на 390 px **с сессией**
на `/`, `/friends`, `/messages`, `/u/andrey`, `/new` — везде ровно 390 (было
~745). Десктопная шапка не изменилась ни на пиксель. Точка-уведомление снята
на аккаунте `zer` — у `andrey` висеть нечему.

### После перекраски: поле тетради, манифест, свой плеер (2026-08-31)

Хвост мелочей, каждая — отдельным решением разработчика, а не пакетом.

| Файл | Что там |
|---|---|
| `app/globals.css` | **Вертикальное поле тетради** — та линия, за которую в тетради не заходят. Живёт на `html::before`, **а не вторым слоем в `body::before`**: у линовки своя геометрия, и подмешивать туда ещё градиент значило бы переписывать оба разом ради правки одного (`body::after` занято зерном, `html::before` было свободно). Привязано **к колонке содержимого, а не к краю экрана**: `left: calc(50% - 34rem)`, то есть на 2rem левее колонки `max-w-5xl`. Включается только с `72rem` — ниже поля нет вовсе, и линия прошла бы по тексту. Замерено: на 1440 px линия на 176 px, на самой границе 1152 px — на 32 px, всегда левее колонки; на 1100 и 390 её нет. Свой токен `--rule-margin` (терракота на 16%), пара значений в тёмной теме. Маска сверху — та же, что у линовки |
| `app/manifest.ts` | **PWA-манифест.** Файловая конвенция App Router: Next сам отдаёт `/manifest.webmanifest` и вписывает `<link rel="manifest">`. Что даёт: «Установить на главный экран» — своё окно без адресной строки, своя иконка. Чего **не** даёт: офлайна (нужен service worker, которого в проекте нет) и попадания в App Store / Google Play. `theme_color` — цвет бумаги, а не акцента: им же красится системная полоса на Android, и приложение должно выглядеть тетрадью |
| `public/icon-192.png`, `icon-512.png`, `icon-maskable-512.png` | Растр из того же знака. **Почему не `app/icon.svg` прямо в манифесте:** SVG в манифесте принимают не все системы, а Android для установки хочет 192 и 512 пикселей. **Maskable-версия обязательна отдельно:** Android режет иконку под свою форму (круг, сквиркл), и у обычной обрезало бы края всплеска — у maskable фон во всю площадь без скруглений и знак ужат до 62% к центру. Отрисованы headless-браузером из inline-SVG, **новых зависимостей в проекте не появилось** (rasterizer вроде `sharp` не ставился) |
| `components/TrackRow.tsx` | **Стал клиентским** ради общего плеера. Раньше здесь стоял нативный `<audio controls>` — не только единственный кусок браузерного хрома в дизайне, но и **второй, независимый способ слушать**: обложка в карточке ходит через `usePreviewPlayer`, строка играла сама по себе, и два превью могли зазвучать хором. Теперь круглая кнопка справа, залитая акцентом ровно пока звучит (состояние, не действие — то же различие, что развело `pillButton` и `pillButtonActive`). Появился проп `trackId`: **своего поля у типа нет намеренно** — в поиске это `Track.id` из базы, в пикере `externalId` от iTunes, у которого строки в базе ещё нет. Осознанно потеряны перемотка и громкость, которые нативный элемент давал даром: превью длится 30 секунд, перематывать нечего. Глифы play/pause продублированы из `TrackArtwork` — там они тоже локальные, и делать один компонент владельцем иконок другого было бы связью на ровном месте |

**Грабля Playwright, если снова придётся снимать пикер трека:** селектор
`dialog input` матчит **закрытую** модалку поиска из шапки — она в DOM всегда.
Нужен `dialog[open] input`. Ошибка выглядит как «поле не видно» при исправном
коде.

Короткий русский месяц приходит с точкой («авг.», кроме мая), она снимается регуляркой |
| `app/globals.css` | `--color-rule-margin` добавлен в `@theme inline` — токен был только фоновым, а теперь нужен классом `border-rule-margin`. Тёмная тема достаётся сама, как у всей палитры |

**Починено заодно — предсуществующее горизонтальное переполнение ленты.**
Замер на главной: документ 1146 px при вьюпорте 900 и 1024, то есть страница
ехала вбок на узком десктопе **ещё до этой правки** (проверено `git stash`);
колонка-поле добавляла к этому свои 56 px и вытаскивала переполнение уже
на 1280. Виноват не сайдбар, хотя за экран уезжал именно он: `truncate` —
это `white-space: nowrap`, и **обрезанный многоточием текст всё равно
сообщает родителю свою полную ширину** как min-content. Длинные названия
треков («Сансара (feat. …, …, …)») распирали `<main>`, а он в `app/page.tsx`
был `flex-1` **без `min-w-0`** — флекс-элемент по умолчанию не сжимается
ниже min-content и выталкивал соседа. Лечится одним `min-w-0` у `<main>`;
после него `scrollWidth` ровно равен вьюпорту на 1280 / 1024 / 900 / 768 /
640 / 390, а длинные названия наконец действительно обрезаются многоточием.
**Правило на будущее:** `truncate` ограничивает ширину только внутри цепочки
предков, где у каждого флекс-звена есть `min-w-0` — сам по себе он её не
держит.

## Data model (Prisma)
 
Ключевые модели: `User`, `Track`, `Post`, `PostTrack`, `Comment`, `Like`, `Follow`.
`Post` привязан к одному `User` (автор) и может содержать несколько `Track`
через join-таблицу `PostTrack` (many-to-many, с полем `position` для порядка
треков в посте). `Track` кешируется по `externalId`, чтобы не дублировать
записи и не дёргать внешний API повторно для уже залогированных треков.
Полная схема — в `prisma/schema.prisma`.

## Технические детали версий (сверено вручную с доками, не полагаться на training data)

**У Prisma есть собственные официальные Claude Code skills** — `npx prisma init` сам ставит их в `.claude/skills/prisma-*` (источник — репозиторий `prisma/skills` на GitHub, см. `skills-lock.json`). Там же лежит `prisma-upgrade-v7` — актуальный гайд по breaking changes от самой Prisma. **Перед тем как гуглить/WebFetch доки Prisma — сначала проверить `.claude/skills/prisma-*/SKILL.md` и `references/*.md` внутри, они уже могут быть локально.**

**Prisma 7** сломал привычный способ работы с клиентом по сравнению с версиями ≤6:
- В `generator client` теперь обязателен явный `output` (например `output = "../generated/prisma"`), провайдер — `"prisma-client"` (не `"prisma-client-js"`)
- Клиент импортируется из сгенерированной папки в проекте (`@/generated/prisma/client` — в `generated/prisma/` нет `index.ts`, только `client.ts`/`browser.ts`), а **не** из `@prisma/client`
- Обязателен driver adapter поверх обычного JS-драйвера (нет больше встроенного Rust-бинарника-движка). Для Postgres — `@prisma/adapter-pg` + `pg`:
  ```ts
  import { PrismaPg } from "@prisma/adapter-pg";
  import { PrismaClient } from "@/generated/prisma/client";

  const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
  const prisma = new PrismaClient({ adapter });
  ```
- **`url`/`directUrl`/`shadowDatabaseUrl` больше не живут в `schema.prisma`!** Блок `datasource` там теперь содержит только `provider = "postgresql"`. Реальные connection-строки переехали в `prisma.config.ts` → `defineConfig({ datasource: { url } })`. **Важно:** `directUrl` в реальном типе `Datasource` не существует (только `url`/`shadowDatabaseUrl`) — подробности и правильная схема ниже.
- `prisma.config.ts` выполняется Prisma CLI как отдельный Node-скрипт, **вне** Next.js — поэтому `.env.local` он не подхватывает автоматически (Next.js грузит `.env.local` только для своего рантайма). Нужен явный `dotenv`: `import { config } from "dotenv"; config({ path: ".env.local" });` в начале `prisma.config.ts`, и сам пакет `dotenv` должен быть явной зависимостью в `package.json` (а не транзитивной).

**Better Auth** (v1.6.x) — пакет называется просто `better-auth` (не `@better-auth/*`). Prisma-адаптер — `prismaAdapter` из `better-auth/adapters/prisma`. CLI для генерации схемы — `npx auth@latest generate` (пакет CLI называется `auth`), дописывает модели `User`/`Session`/`Account`/`Verification` в `schema.prisma`, читая конфиг из `lib/auth.ts` — то есть `lib/auth.ts` должен существовать и импортироваться без ошибок **до** запуска этой команды.

**Supabase + Prisma подключение** — нужны два разных URL на одну и ту же БД:
- `DATABASE_URL` — transaction pooler, порт 6543, `?pgbouncer=true` — для рантайма приложения
- `DIRECT_URL` — session pooler, порт 5432, без `pgbouncer` — для `prisma migrate` (настоящий direct-connect у Supabase только по IPv6; session pooler — IPv4-совместимая замена, которая в отличие от transaction pooler поддерживает миграции)

**`P1001: Can't reach database server` от Prisma не всегда значит проблему с сетью** — через pgbouncer (transaction pooler, порт 6543) эта ошибка может маскировать обычный `28P01: password authentication failed`. Если TCP-соединение до хоста при этом раскрывается нормально (проверить `Test-NetConnection`/аналог) — не тратить время на сетевую диагностику, а сразу проверить сам пароль прямым тестовым подключением через `pg` (`new pg.Client({connectionString}).connect()`), это даёт настоящую причину.

**Вторая причина того же `P1001` — мёртвый NAT64-IPv6 (поймано 2026-08-19).** Если `pg` из Node подключается тем же URL, а CLI нет — дело не в сети и не в пароле: DNS отдаёт сначала адреса `64:ff9b::…`, они не отвечают, Node 20+ спасается Happy Eyeballs (`autoSelectFamily`, пробует оба семейства параллельно), а Rust-движок Prisma берёт первый адрес и падает. Обход — обёртка, которая резолвит IPv4 (`dns.resolve4`) и подменяет хост в `DIRECT_URL` только на время запуска CLI; `.env.local` и `prisma.config.ts` не трогать. Работает потому, что пулер Supabase маршрутизирует тенант по имени пользователя, а не по хосту.

**`directUrl` в `prisma.config.ts` не существует — реальная причина плавающих зависаний/ошибок `migrate`/`db push` (найдено 2026-08-06 через `npx tsc --noEmit`).** Тип `Datasource` в `@prisma/config` (`node_modules/@prisma/config/dist/index.d.ts`) содержит только `url` и `shadowDatabaseUrl` — поля `directUrl` там нет и не было, несмотря на то что так же писал даже один из референсов официального skill `prisma-upgrade-v7` (`references/prisma-config.md` — расхождение с реальным типом, не доверять слепо и этим референсам, перепроверять tsc'ом). Поле тихо игнорировалось (конфиг грузится без тайпчека), из-за чего CLI-команды всё это время ходили через `DATABASE_URL` (transaction pooler, порт 6543) вместо `DIRECT_URL` — а pgbouncer в transaction-режиме не гарантирует операции уровня сессии, нужные миграциям (advisory locks, `CREATE DATABASE` для shadow-базы). Отсюда нестабильность: то зависание, то `P1001`, то `P1000` — в отличие от простых запросов через голый `pg`, которые транзакционный pooler спокойно тянет.

**Правило:** в `prisma.config.ts` → `datasource` класть **только** `url`, и туда должен идти `DIRECT_URL` (session pooler), а не пулированный `DATABASE_URL`. `DATABASE_URL` нужен исключительно рантайму приложения (driver adapter в коде, `lib/auth.ts` и т.п.) — `prisma.config.ts` он не касается вообще, это конфиг только для CLI-тулинга (migrate/db push/studio).

**После изменения схемы дев-сервер надо перезапустить, hot-reload не спасает** (поймано 2026-08-17 на `ignoredAt`). `next dev` держит в памяти *старый* сгенерированный клиент, и запрос с новым полем падает рантайм-ошибкой `PrismaClientValidationError: Unknown argument 'X'` — при том что `npx tsc --noEmit` уже зелёный (он читает свежие типы с диска). Симптом обманчивый: выглядит как «фича не работает», а не как «сервер устарел». Порядок: `migrate dev` → `generate` → **перезапуск** `npm run dev`. И `npx prisma generate` после `migrate dev` лишним не бывает — клиент не всегда обновляется сам.

**Если Prisma CLI видит, что её вызывает AI-агент** (Claude Code и подобные) — она блокирует опасные команды типа `migrate reset` без явного согласия человека и просит перезапустить с `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION=<точный текст согласия пользователя>`. Это встроенная защита самой Prisma, не баг — всегда спрашивать пользователя перед таким перезапуском, не обходить.

## Внешние API
 
**Основной — iTunes Search API** (`https://itunes.apple.com/search`)
- без ключа, ~20 запросов/минуту на IP (неофициальный лимит) — обязателен дебаунс на поиске
- отдаёт title, artist, album, artworkUrl, 30-сек previewUrl
**Резервный — MusicBrainz API** (`https://musicbrainz.org/ws/2/`)
- без ключа, но обязателен свой `User-Agent` заголовок
- лимит 1 запрос/секунду на IP — превышение временно блокирует IP
- используется, если iTunes не нашёл трек
Оба запроса — **только на сервере** (server actions / route handlers), никогда
с клиента: у MusicBrainz нужен кастомный заголовок, а лимиты обоих API считаются
по IP, так что их надо контролировать централизованно и кешировать.
 
## Поиск по сайту (реализовано 2026-08-13)

Важно не путать с поиском трека на `/new` (это поиск во внешнем iTunes/MusicBrainz
API при создании поста, уже описан выше в "Внешние API"). Здесь речь о другом —
о сквозном поиске по уже своим данным: посты, треки, пользователи. Движок —
встроенный полнотекстовый поиск Postgres, без сторонних сервисов
(Meilisearch/Algolia) — не тащим новую инфраструктуру, пока нет реальной нагрузки.

Что неочевидно и стоит помнить:

- **Индексы живут только в миграции, не в `schema.prisma`.** Prisma не умеет
  объявлять `tsvector`/GIN — три expression-индекса написаны руками
  (`prisma/migrations/*_add_fulltext_search_indexes/`). Выбраны expression-индексы
  (`USING GIN (to_tsvector(...))`), а не хранимая generated-колонка: индекс сам
  всегда синхронен с данными, ни новой колонки, ни триггера. **Проверено:
  дрейфом Prisma это не считает** (`migrate diff` → пусто, `migrate dev` →
  "Already in sync"), удалить не предложит. Обратная сторона: `schema.prisma`
  больше не полное описание БД — про эти индексы знает только папка миграций.
- **Выражение в `WHERE` должно буквально совпадать с выражением в индексе**,
  иначе Postgres индекс не подхватит. Отсюда дублирование `to_tsvector(...)`
  в `WHERE` и в `ORDER BY ts_rank(...)` в `lib/search.ts` — это не копипаста
  по недосмотру.
- **Колонки в склейке обязаны быть NOT NULL.** В SQL `'текст' || NULL` = `NULL`,
  так что одно nullable-поле в `title || ' ' || artist` тихо выкинуло бы строку
  из индекса. Сейчас все четыре склеиваемых поля NOT NULL — при изменении схемы
  перепроверить.
- **`websearch_to_tsquery`, а не `to_tsquery`** — не падает на произвольном
  пользовательском вводе (одиночные `!`, `&`, кавычки), плюс даёт Google-подобный
  синтаксис (`"фраза"`, `or`, `-исключение`). `to_tsquery` на мусоре кидает
  исключение → 500 на публичной странице.
- **`'russian'` для постов, `'simple'` для треков/юзеров.** Постам нужен
  стемминг («замечательные» находит «замечательный»), именам и названиям он бы
  только мешал, и они не обязательно на русском.
- **Префиксного поиска нет** — FTS матчит слова/основы целиком, `zer` не найдёт
  `ZeroneR`. Это ограничение движка, не баг. Если понадобится тайпахед —
  отдельным шагом через `pg_trgm` или `to_tsquery` с `:*`.
- **Отлаживать поиск с кириллицей из Git Bash нельзя** — шелл на Windows отдаёт
  аргументы в cp1251, `curl --data-urlencode` честно закодирует битые байты, и
  получится ложный вывод "кириллица не ищется" при исправном коде. Проверять
  Node-скриптом (файл в UTF-8) или из браузера.

## Про разработчика
 
Solo-разработчик уровня junior-to-middle, возвращается к активной разработке
после ~7 лет перерыва в React-экосистеме. Стек в целом знаком, но многое нужно
вспоминать заново — не считать полным новичком, но и не считать, что все
детали текущих версий инструментов держатся в голове. Работает через агента
(Claude Code) — пишет код агент, разработчик разбирается в результате и
принимает архитектурные решения. Общение — на русском, английские технические
термины сохранять как есть, не переводить.

У разработчика может быть нестабильный интернет (специфика места работы) — это
норма, а не признак проблемы в проекте/коде. Обрывы вида `ECONNRESET` на
`npm install` или `P1001: Can't reach database server` на `prisma migrate`
чаще всего чинятся простым повтором команды. Не нужно тратить время на
глубокую диагностику сети при первом же сбое — сначала просто retry.
 
## Роль агента
 
Функционируй как senior-ментор, а не просто "исполнитель тикетов":
 
- Перед не тривиальными изменениями — объясняй рассуждение (почему именно так, а не только что делаешь)
- После изменений — коротко резюмируй, что сделано и почему именно таким способом
- Во время работы (не только до/после) — периодически поясняй, что именно сейчас делаешь, особенно на длинных многошаговых задачах, а не молчи до самого результата
- Не вываливай код без объяснения, если разработчик не попросил явно "просто сделай"
- Для сложных/многофайловых задач — сначала предлагай план (Plan Mode), не бросайся сразу в правки
- Мелкие, проверяемые шаги вместо одного большого изменения на всю фичу
- Предпочтительный формат ответов — структурированные таблицы и короткие абзацы, не длинная проза
- Если задача расплывчата — уточни, не додумывай архитектурные решения молча
- Обращение — на "ты", без официоза
- Уместны шутки, когда ситуация располагает (не в каждом ответе через силу)
- Смайлики приветствуются 🙂
- Разрешаю иногда (когда это уместно) спорить со мной (когда ты уверен в том что ты прав) и даже на повышенных тонах. Ведь в спорах рождается истина.

## Обучение

Для разработчика важен не только рабочий результат, но и понимание —
это осознанное совмещение разработки с изучением/освежением стека. Поэтому:

- Объясняй не только "почему выбрано такое решение", но и "как это устроено
  и работает" — на уровне, достаточном чтобы дальше действовать самостоятельно
- Если есть несколько способов сделать одно и то же — кратко называй
  альтернативы и почему выбран именно этот
- Не бойся давать чуть больше контекста, чем нужно для конкретной задачи,
  если это помогает понять механизм, а не просто скопировать код
- Если нужно представить план (например, из Plan Mode) — сначала простыми
  словами, через аналогию с уже сделанным в проекте (пример: аватарка —
  такая же ссылка, как обложка трека, ничего нового изобретать не надо).
  Технические детали (имена файлов, конкретные API) — только по запросу.
  Файл плана — это шпаргалка для самого агента на следующую сессию, не текст
  для разработчика; не пересказывать его как есть.
- Объяснять код лучше по шагам прямо во время реализации, а не одной стеной
  текста заранее — так усваивается лучше (сработало 2026-08-08 на примере
  сессии про аватар: стена терминов про Server Actions/RLS/service_role не
  зашла, а аналогия с обложкой трека и обещание объяснять по ходу — зашли)

## Чего избегать
 
- Не дублировать логику запроса к трек-API в разных местах — один общий модуль-обёртка
- Не хранить обложки/превью треков в своём storage — только ссылки от API
- Не давать доступ на редактирование/удаление чужих постов ни при каких условиях
